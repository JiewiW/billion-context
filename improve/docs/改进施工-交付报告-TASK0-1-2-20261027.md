### 3.1 语义（与计划书单点定义完全一致）

- `userVerbatimKeep = 0` ⇔ **方案 A** ⇔ 全部 user 消息原文保留，永不进压缩范围。
- `userVerbatimKeep = N > 0` ⇔ **方案 B** ⇔ 只保留最近 N 条，更老的允许进 T3。
- **没有「不保护」的取值**，这是设计而非缺口。

### 3.4 计划书未覆盖、但必须做的宿主侧改动（3 处，请复核）

这 3 处不在施工单的落点清单里，但不做则方案 A/B 在宿主上是**不可用**的：

1. **`bcdsh/src/region.ts` 新增 `liveRefOf(byRaw, key)`** —— 把 `BLOCKED` 视同「无 ref」。
   改前 bcdsh 源码里 `BLOCKED` **零命中**，受保护 user 的 `BLOCKED` 会被直接当边界 ref 交给内核，
   报 `Invalid boundary ref(s): startId="BLOCKED"`。已接入 `tools.ts:anchorRefForNode` 与
   `index.ts` 三处 `byRaw` 直查。这与内核 `boundaries.ts:344` 的跳过语义对齐。
2. **`bcdsh/src/index.ts` 的 `env` 字面量补 `get userVerbatimKeep()`** —— 漏掉这行会让
   `AcpConfig.userVerbatimKeep` 变成**死键**：pre-step 与 `compactForOverflow` 都走
   `kernelConfigFor({ ...this.env })`，env 上没有该键就只剩 `coreOverrides` 能改它，
   插件配置里写的值被静默忽略、内核永远退回 0。实测已复现并修复。
3. **`acpk/src/report.ts` 的统计口径** —— 受保护 user 是 `BLOCKED`、无 ref，`collectVisible`
   会把它们整个跳过，所以「user messages: N msgs」若从 `visible` 数会**恒为 0**，把
   「全部 user 都受保护」显示成「一条都没有」。已改为从原始 `messages` 数。

### 3.6 已登记的偏差与代价（请知悉）

1. **宿主默认 12 的由来**：按你的裁决落地。理由：宿主的压缩单元是**包含旧 user 轮的会话跨度**，
   若宿主也取 0，任何含 user 轮的跨度都会被整段硬拒，压缩能力直接归零（实测 bcdsh 从
   404 pass 掉到 73 fail）。真实会话有几百个 user 轮，N=12 只保护最近 12 轮，生产上可用；
   但**合成测试会话往往不足 12 个 user 轮**，因此宿主测试的 env 需显式给 `userVerbatimKeep: 1`
   （= 复现宿主原有的「只有最新 user 轮受保护」语义）。
2. **方案 A 的已知代价**：user 文本不再作为压缩余量，纯文本会话更容易进 `stuck`。
   已在 `terminal-escape.test.ts` 用对照用例固定这一因果（keep=0 → maxPending=0 → streak 1；
   keep=1 → maxPending=15000 → streak 0），不是靠放宽断言混过去。
3. **一次性测试翻新规模**：acpk 约 100 条用例、bcdsh 约 80 条用例因「`msg()` 默认 role=user
   的占位消息现在成了不可折叠的圣物」而失效。翻新只用两种不改语义的手段：
   ① env/config 显式给 `userVerbatimKeep`；② 占位消息显式写成 `assistant`（范围覆盖全量时唯一解）。
   **没有任何 `assert` 被删除、放宽或改数值**；无 `.skip` / `.todo` 新增。
