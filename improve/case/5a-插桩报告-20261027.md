## 1. 口径（复算时按这一节）

| 项 | 定义 |
|---|---|
| 候选块 | 每条消息经 `messages.extractText` 提取出的文本：只取 `type === 'text'` 的块 + 递归 `block.content` + image/file 占位符，块间用 `\n` 连接。**这就是真正进模型上下文的那部分**（2026-10-28 修正，原口径见 §2.1） |
| 消息 id 去重 | `agent/inbox/spliced` 的 inserted 与其后 `user/message` 若为同一 id，只算一次（本次跳过 39 块）|
| 块长下限 | 800 字符（与 `dedup-recount.js` 同口径）|
| 指纹 | 前 120 字符（`fp120`），**不归一化空白**（与 `dedup-recount.js` 完全一致）|
| 重复组 | 同指纹、组内 ≥ 2 块 |
| 单份 | 组内最大块长 |
| **浪费** | **Σ(sum − single)**：组内除最大那份以外的全部块长 |
| 总量 | 全部候选块字符数之和（459 块 = 804,575 字符）|

**为什么「浪费」不是「合计」**：合计 Σsum 把每组的首份也计入。首份是必要开销，不是浪费。
本次两口径都算了，方便和旧数字对照：**Σsum = 617,746 字符**，**Σwaste = 370,965 字符**。

## 2. 与 273,017 口径的差异声明（AC-3.3）

计划书 §6 写的是「273,017 字符 = tool 角色块重复合计」。本报告的数字**不能**与之直接相加或相互校验，
三处口径不同：

| 维度 | 273,017（旧口径） | 本报告（新口径） |
|---|---|---|
| 角色范围 | **只统计 tool 角色块** | 全角色（user / assistant / tool / system）|
| 指标定义 | Σsum（组内全部块长之和，含首份） | Σwaste = Σ(sum − single)，剔首份 |
| 消息 id 去重 | 无（同一消息在 spliced 与 user/message 各出现一次会重复计数）| 有（跳过 39 块）|
| 重复组数 | 11 组 | 16 组 |

按**同一角色**（tool）对照更清楚：本报告 tool 通道 **Σsum = 223,277**、**Σwaste = 41,587**；
旧口径 273,017 落在两者之间——差在 id 去重（旧口径把「同一条 tool 结果在 inbox 里出现一次、
在 tool/result 里又出现一次」算成 2 份）。

**结论**：273,017 是「重复内容上界」的旧估计，本报告 370,965 是「剔除首份后的真实浪费」。
两者量纲同为字符，但定义与角色范围不同，**任何「节省了 X%」的说法都必须标明用的哪一个**。

## 2.1 口径修正（2026-10-28，插桩补口时发现）

补 TASK-3 的插桩覆盖缺口时，发现**线上插桩与本报告的回放口径一直对不上账**，
于是把两边的文本口径统一到投影用的 `messages.extractText`。差异与影响：

| 维度 | 修正前（线上插桩） | 修正前（本报告回放） | 修正后（两边一致） |
|---|---|---|---|
| `reasoning` 块 | **被计入**（只看块上有没有 `text` 字段） | 不计入（只取 `type === 'text'`） | 不计入 |
| `block.content` 递归 | 递归任意 `content` | 不递归 | 只递归数组 |
| 块之间连接 | 无分隔直接累加 | 无分隔直接累加 | `\n`（与投影一致） |
| image/file 占位符 | 不计入 | 不计入 | 计入（与投影一致） |

`reasoning` 块是模型的内心戏，**投影时压根不发给模型**（`extractText` 不取它），
算进去等于把没进上下文的内容算成"注入量"。实测这一项让 20 个真实会话多算
**4105 行 / 1528 万字符**。

修正后，本报告的数字变化如下（**结论不变**）：

| 指标 | 修正前 | 修正后 | 变化 |
|---|---|---|---|
| 消息块 | 459 | 460 | +1 |
| 总字符 | 804,575 | 804,860 | +285（+0.04%） |
| **浪费字符** | 370,965 | **370,969** | +4（+0.001%） |
| **浪费占比** | 46.11% | **46.09%** | -0.02 个百分点 |
| 重复组数 | 16 | 16 | 0 |
| runtime-context 占重复总计 | 64.11% | **64.11%** | **0（完全不变）** |
| 期 2（快照折叠后）占比 | 23.87% | 23.85% | -0.02 个百分点 |

**TASK-4 的决策依据不受影响**：`runtime-context` 64.11% 仍在「≥ 30%」与「< 70%」之间，
第一行仍是「内容寻址缓存，只注入增量」，仍不触发"按最大类直选"的特殊裁决。

## 5. 插桩口径的边界与未做项（如实声明）

1. **没有跑运行中的 DSH 实例**。ENV-6 明确「把改动后的 bcdsh 产物接入实例的安装流程未确认」，
   且 web profile 的 `dsh.bundles` 里没装本插件（TASK-0 结论）。本报告用**同一份真实会话数据回放**，
   分类走**同一份** `classifySurfaceEvent`，插桩落点与线上完全一致；差别只在「不是活实例的实时采集」。
   → AC-3.1 的判据（jsonl 存在 + 每行可 `JSON.parse`）在回放产物上**实测通过**
   （460 行、0 行缺字段），但"活实例采集"这一条记 **未做动态验证**。
2. **【2026-10-28 已补】插桩覆盖缺口 —— 原先只覆盖 surface 事件。**
   原挂点是 `classifySurfaceEvent`，而它是 **surface 事件**的分类点，由此有两个漏：
   - `agent/inbox/spliced` 通道的消息不是 surface 事件（`data.inserted` 里装的是消息对象），
     **永远不会被分类** —— 线上活采集整条漏掉这个通道。
   - `assistant/message` 与 `tool/result` 两个通道**只有会话真的发生压缩时**才被分类
     （分类器的调用点只有保护尾扫描和可压缩范围扫描，后者要等模型请求压缩才跑），
     采集覆盖会随会话压力浮动，短会话一行都记不到。

   补法：新增 `messages.traceSessionEvents(session)` —— 宿主 `agent/pre-step` 钩子（每步必过、
   且在 `autoNudge` 早退之前）里**主动全量扫一遍**会话日志，覆盖
   `user/message` / `assistant/message` / `tool/result` / `compaction/summary`
   四个事件类型 + `agent/inbox/spliced` 通道。分类器不再自己写盘，**写盘只有这一个入口**
   （两个入口同时存在就会把同一条消息记两遍）。

   配套的两处必要修正（都在补口时实测发现）：
   - **跨通道去重**：同一条消息先出现在 spliced 通道（宿主插进 inbox），随后又以
     `user/message` 出现一次（实测按 id 匹配率 **99.22%**）。不去重，"重复注入浪费量"
     会虚高一倍。解法：两通道共享一张消息 id 去重表。
   - **去重键按会话隔开**：`seq` 是会话内序号，不同会话必然重号。早先的 `type#seq` 键
     在多会话场景下会把后一个会话的大量事件误判成"已记过"而跳过（实测 20 个会话
     **少记 5820 行**）。解法：去重键加会话 id 作命名空间。

   补完后做了一次**线上 vs 回放逐条对账**（20 个真实会话）：行数、字符数、四分类分布、
   指纹集合**完全一致**（28064 行 / 37,051,401 字符 / 指纹差 0）。
3. `chars` 是**字符数**，不是 token。插桩的 `collectText` 现已与 `messages.extractText`
   **逐字同口径**（见 §2.1）；两处实现各写一份（反向 import 会循环依赖），所以改动时
   必须同步改，否则两边又对不上账。
4. `trigger` 恒为 `unknown`：分类点拿不到上游触发原因，按计划书【禁止】编造。
5. 只有一个真实会话。样本量 1 → 占比是「这一个会话」的事实，不是全网分布；TASK-4 的 30% 判据
   按「单类 ≥ 70% 才按最大类直选」的修订规则复核：64.11% 未触发特殊裁决。
   （补口时另取了 20 个真实会话做覆盖统计，见 §7。）

## 7. 补口时的覆盖统计（2026-10-28）

补 TASK-3 时先量了"漏的到底有多少"，20 个真实会话：

| 项 | 数值 |
|---|---|
| `user/message` 事件 | 5,951 |
| `agent/inbox/spliced` 事件 | 5,026（其中 1,956 个是只有删除、没有插入）|
| spliced 插入的消息（有文本）| 3,070 条 |
| 其中后来也以 `user/message` 出现（按 id）| 3,046 条（**99.22%**）|
| **只在 spliced 出现、插桩原先完全看不到** | **13 条 / 9,522 字符** |

**结论**：原先"插桩漏掉最大一条通道"的说法在**条数上**是对的（spliced 是最大的通道），
但**实际漏掉的独有内容极少** —— 99.22% 的 spliced 内容后来都成了 `user/message`，
已被插桩覆盖。

这不意味着可以不补：补之前**线上采到的 assistant / tool 两个通道本身就不可靠**
（只记了会话发生压缩那部分，见 §5.2），而且一旦补了 spliced 而不做跨通道去重，
99.22% 的重复会让"重复注入浪费量"虚高一倍。

⚠️ **另有一个连带发现（不在本轮范围）**：spliced 通道里的宿主注入行里，
`plugin:dsh-cot-anchor` 一类占 2,529 条 / 108 万字符（重叠部分），它们的分类是
`instruction` —— 即"不可折叠的策略行"。这部分重复注入是 TASK-4 的处置对象，不是 TASK-3 的。
